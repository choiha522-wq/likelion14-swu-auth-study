# 세션 vs JWT 비교

## 인증 상태를 어디에서 관리하는가

- **세션:** 로그인한 사용자 상태는 서버가 관리합니다. 클라이언트는 세션 ID를 쿠키로 보내고, 서버는 세션 저장소에서 상태를 확인합니다.
- **JWT:** 서버가 서명한 토큰을 클라이언트가 보관하고 요청마다 보냅니다. 서버는 서명, 유효기간, 토큰 용도와 권한 등을 확인합니다.

JWT의 페이로드는 서명만 된 경우 암호화되지 않습니다. 토큰을 가진 사람은 페이로드를 읽을 수 있으므로 비밀번호나 불필요한 민감 정보를 넣지 않습니다.

## 트레이드오프

| 관점 | 세션 | JWT |
|---|---|---|
| 로그아웃 | 서버에서 세션을 삭제해 즉시 무효화하기 쉬움 | Access Token 폐기 목록이나 짧은 만료 시간이 필요할 수 있음 |
| 수평 확장 | 서버 간 세션 공유가 필요할 수 있음 | 서명 키를 공유하면 각 서버에서 검증할 수 있으나, 권한 변경·토큰 폐기와 Refresh Token 저장은 별도 관리 |
| 저장소 의존성 | 세션 저장소 조회 | 저장소 조회 없이 검증 가능. 단, 폐기 목록 또는 Refresh Token 상태를 확인하면 저장소가 다시 필요 |
| 토큰/식별자 탈취 | 세션 ID가 유효한 동안 악용 가능 | 토큰이 유효한 동안 재사용 가능 |
| 구현·운영 | 세션 저장소와 만료 정책 관리 | 서명 키, 만료, 재발급, Refresh Token 회전·폐기 정책 관리 |

세션과 JWT 중 하나가 항상 우월한 것은 아닙니다. 서버에서 로그아웃과 인증 상태를 즉시 통제하기 원하면 세션이 단순할 수 있고, 여러 API 간 토큰 전달이 필요하면 JWT가 적합할 수 있습니다. 선택은 시스템 구조와 무효화 요구사항에 맞춰야 합니다.

## 이 저장소의 단계별 구현

- `1week`, `2week`: 세션 ID 기반 인증을 직접 구현한 뒤 Spring Security 폼 로그인과 BCrypt로 확장
- `3week`: JWT 발급과 서명·만료 검증
- `4week`: `/api/**` 전용 무상태 필터 체인과 역할 기반 접근 제어
- `5week`: HttpOnly Refresh 쿠키, 서버 해시 저장, 토큰 회전과 로그아웃
- `6week`: 최종 통합 설명과 실행 흐름

JWT용 `/api/**` 체인과 세션 학습용 경로를 분리했습니다. Refresh Token 저장은 인메모리 기반이라 재시작 시 사라지고 여러 서버가 상태를 공유하지 않습니다.
